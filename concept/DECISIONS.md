# Registro de decisiones

Decisiones de diseño tomadas al construir Katse, en el orden en que aparecieron. Cada una dice qué se decidió, por qué, y qué se descartó.

| # | Decisión | Por qué | Alternativa descartada |
|---|---|---|---|
| 1 | **Reproducir en lugar de leer.** El eje del concepto son tres niveles de reproducción | Leer línea a línea no escala con el código generado por agentes. Reproducir sí, porque generar es barato | Un agente revisor que lee el diff y opina: es justo «la IA dijo que estaba bien» |
| 2 | **La herramienta nunca aprueba ni hace merge.** Solo mezcla en una copia para probar | El reto exige una persona con nombre responsable de cada cambio | Merge automático cuando todo sale verde |
| 3 | **Reglas legibles en lugar de una puntuación.** El carril sale de reglas con nombre, y el informe enseña cuáles se dispararon y cuáles no | El reto rechaza las puntuaciones de riesgo que nadie sabe explicar | Un porcentaje de confianza por PR |
| 4 | **No quedarse con «la mejor» réplica.** Las réplicas son evidencia para revisar el PR, no sustitutos | Elegir automáticamente otra versión sería la IA aprobando y reescribiendo | Torneo entre versiones y merge de la ganadora |
| 5 | **El consenso entre réplicas solo dirige la atención.** Nunca cuenta como prueba | Réplicas del mismo modelo comparten puntos ciegos: pueden coincidir en el mismo error | Votación por mayoría |
| 6 | **El número de réplicas depende del riesgo, no de las líneas.** Sin réplicas en la verificación rápida, tres por defecto en la completa | Las réplicas son la etapa cara. No se llama «estadísticamente significativo» porque las réplicas no son independientes | N fijo o proporcional al tamaño del diff |
| 7 | **Un PR es una rama por delante de la base.** Recibir = ramas remotas; enviar = ramas locales sin subir | Funciona con cualquier repo git, sin depender de la API de un proveedor ni de credenciales | Integrarse solo con la API de GitHub |
| 8 | **La base se detecta de `origin/HEAD` y se enseña siempre.** Se puede cambiar en los ajustes | En el repo del reto la base real no era `master`: las ramas salían de otra rama 235 commits atrás | Asumir `main` o `master` |
| 9 | **Antes de culpar al PR, se comprueba la base.** Si algo no compila o falla con el PR, se prueba sin él | En la primera ejecución la herramienta devolvió un PR por un proyecto de tests que tampoco compilaba sin el PR | Tratar cualquier fallo de compilación como culpa del cambio |
| 10 | **Lo que no se ejecuta se dice.** Un test que el sandbox no puede ejecutar sale como «no ejecutado» y genera una pregunta | Callarlo equivale a darlo por bueno | Ignorar los proyectos que no compilan |
| 11 | **Las réplicas trabajan sobre una copia sin historial.** No es un worktree: es una exportación del commit base con un repositorio nuevo | En un worktree el agente puede ver la rama del PR con `git log --all` | Worktrees de git para todo |
| 12 | **Tres capas de aislamiento para los agentes:** copia sin historial, sandbox del sistema y comprobación del repo original antes y después | En la primera ejecución los agentes trabajaron dentro del repo original (ver LESSONS, punto 1) | Confiar en el directorio de trabajo del proceso |
| 13 | **Si un agente toca el repo original, se descartan todas las réplicas.** | Su trabajo ya no puede llamarse independiente | Descartar solo la réplica culpable |
| 14 | **Los modelos solo redactan.** El juez formula preguntas y el asistente responde desde el informe. Ninguno tiene veredicto | Así una alucinación solo puede producir una pregunta mal redactada, nunca una aprobación | Un juez que decide si se aprueba |
| 15 | **La evidencia de que un test nuevo sirve es que falle sin el cambio.** Se pasan los tests del PR sobre la base | Un test escrito a la vez que el código puede pasar siempre y no probar nada | Aceptar que los tests del PR pasan con el PR |
| 16 | **Los defectos sembrados miden dos cosas a la vez:** si los tests del PR tienen dientes y si la revisión cazaría un bug conocido | Es la única medida de la calidad del revisor que se puede obtener sin esperar incidentes en producción | Medir solo actividad (comentarios, tiempo) |
| 17 | **Tests cruzados entre el PR y las réplicas.** Un test del PR que otras implementaciones del mismo requisito no pasan fija algo que el requisito no dice | Convierte «las réplicas divergen» de comparación de texto en evidencia ejecutada | Comparar solo el texto de los diffs |
| 18 | **Sin prompt guardado, menos confianza.** Con Entire se usa el prompt original; sin él, el texto de la issue, y el informe lo marca | La procedencia es parte de la evidencia. Las ramas del reto no la traen | Tratar igual un cambio con procedencia que sin ella |
| 19 | **La firma exige esfuerzo.** Responder cada pregunta, confirmar lo leído y escribir el riesgo aceptado | Reduce el sesgo de automatización: firmar sin mirar | Un botón «Aprobar» |
| 20 | **La confianza es por área y empieza en prueba.** Se gana con cinco cambios firmados sin escapes y se retira con un escape | El reto pide confianza ganada por historial y retirada tras un escape | Confianza global de la herramienta |
| 21 | **Node sin dependencias y una interfaz sin compilación.** | Arranca con `npm start` en cualquier máquina del hackathon | Framework de frontend y base de datos |
| 22 | **Los resultados se guardan fuera del repo del usuario.** La única escritura opcional es `git notes`, bajo petición | «Tu repositorio no se toca» tiene que ser verdad | Escribir el informe dentro del repo revisado |
| 23 | **Una réplica solo cuenta si se sostiene sola:** cambia código de producto, compila y pasa sus propios tests | En una ejecución los agentes se quedaron sin cuota a medias y su trabajo incompleto contó como «divergencia» (ver LESSONS, punto 2) | Contar cualquier réplica que haya cambiado algún fichero |
| 24 | **Comprobación previa de cada agente** con una petición mínima antes de empezar. Si el usuario no eligió los agentes, el que falla se sustituye por el siguiente | Evita gastar minutos en un agente sin cuota o sin sesión, y deja dicho por qué no participó | Descubrirlo cuando el agente falla a mitad |
| 25 | **Si todas las réplicas válidas son de la misma familia de modelo, el informe lo dice** en «no comprobado» | Es un motivo declarado para desconfiar del consenso | Tratar igual tres réplicas del mismo modelo que tres de modelos distintos |
| 26 | **Agentes de prueba basados en parches** (`KATSE_FAKE_AGENTS`) para probar el pipeline sin gastar cuota. Sus resultados se guardan aparte y nunca se presentan como réplicas de agentes | La lógica de comparación y de tests cruzados tiene que poder probarse de forma determinista | Probar solo con agentes reales |
| 27 | **Identidad visual Katse** (logo de ojo, `#0D111C`, `#171D2C`, violeta `#B7A4FF`, Geist e IBM Plex Mono). La esfera del asistente pasa a ser el ojo, que respira en reposo y escanea mientras verifica | Es la identidad que definió el equipo en `visual/`. El ojo encaja con la idea: mira y enseña, no decide | Mantener la esfera cian del primer prototipo |
| 28 | **Las llamadas de redacción también van aisladas:** carpeta vacía, agente de solo lectura y sandbox sin escritura | Un modelo al que solo se pedía texto editó el repositorio revisado (ver LESSONS, punto 3) | Confiar en que un modelo al que se pide texto no usará herramientas |
| 29 | **El repositorio original se comprueba antes y después de toda la verificación**, no solo de las réplicas | Una comprobación limitada a una etapa no ve lo que pasa en las demás | Vigilar solo la etapa de agentes |
